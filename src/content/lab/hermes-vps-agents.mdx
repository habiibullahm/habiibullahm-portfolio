title: "Six Hermes agents on one VPS"
summary: "Six profiles on one gateway, a key in each profile .env, and a loopback dashboard that found cron jobs still pinned to a dead provider."
date: "2026-11-04"
tags: ["Infrastructure", "AI Ops"]
problem:
  - "Hermes Desktop is only the UI. The agents, their memory, and their browser run on the VPS."
  - "A new profile copies the model settings and leaves .env empty, so the first reply fails with no API key."
  - "Cron failures and host state showed up in logs, not on one page."
process:
  - "Kept one gateway for every profile. Put the 9router key in each profile .env, then restarted the user gateway service."
  - "Changed WhatsApp tools with --platform whatsapp. Hermes ignores /start, so a bot that only received /start looked dead."
  - "Served a Python dashboard on 127.0.0.1:19999 through an SSH tunnel. It reads /proc and systemd, and it does not read .env files or message text."
decisions:
  - "One gateway, separate profile folders. A profile is not an OS sandbox, because the Linux user is shared."
  - "Do not copy a paid fallback key into a new profile. Read a SOUL file before installing it."
  - "The dashboard stays on loopback. Swap warns at 40% so this host does not stay red."
learnings:
  - "Non-interactive SSH needs bash -lc to find hermes. A cron job pinned to its own provider ignores the profile default."
  - "display.show_reasoning is the config key. WhatsApp has no read-only mode, so an accepted message gets a reply."
  - "Show GiB so the numbers match df and free. Do not run a cron job that messages someone just to test it."
outcome: "Six profiles run on one gateway. The loopback page found eleven cron jobs still locked to a provider that no longer accepted the key."
